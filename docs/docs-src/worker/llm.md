# llm

**File:** `src/worker/llm.zig`  
**Module:** `worker`  
**Description:** The worker's LLM client — transport splits by destination (loopback plain-http via the in-process httpc.zig socket client; hosted TLS via a curl child that reads the API key's config from its stdin, `-K -`), with `chat()` for one-shot completions and `complete()` for the agentic tool loop.

---

## Purpose Summary

Every model call the worker makes goes through this client. It loads no models: it builds request bodies, moves bytes, and parses replies. A loopback backend (a local Ollama) is spoken to in-process over raw sockets — no curl child (Defender kills those), no scratch files — while a hosted backend needs TLS the Zig control plane lacks, so those calls shell out to curl. curl reads the key from a config written into its stdin, so the key never appears on the process argv and never touches disk. The request body curl sends is a file, the call's own: when the call ends, it becomes the tag's copy that a replay starts from. On top of transport it carries the process's entire token accounting (global meters, per-thread turn deltas, per-role cost buckets) and a startup capability probe that shapes how each backend is driven.

## Key Exports

- `Reply` + `chat(...)` / `chatTemp(...)` — one-shot system+user completion (temp variant sets temperature); `visionExtract(...)` — image bytes + instruction
- `ToolCall` + `Step` (`content`, `reasoning`, `calls`, `ok`, `truncated`, `incomplete`) + `complete(...)` — the agentic entry point: a pre-built messages array + tools array → content OR parsed tool_calls; `truncated` marks a length-cut reply (load-bearing: a fenced file body in a cut reply is incomplete even though it reads clean); `incomplete` marks a streamed reply whose stream never said it ended (no finish_reason, no `[DONE]`, not stopped on our side)
- `completeStream(...)` + `DeltaKind` (`content` / `reasoning` / `tool_progress`) — streaming variant; tests cover both the SSE parser and the Ollama-native parser, including reassembling tool calls from streamed fragments
- `STOPPED` — what a call refused because its turn was stopped answers with (`ok=false`); a stream stopped before it started answers as a Stop mid-stream does instead (ok, nothing streamed)
- Token meters — `tokens_in`/`tokens_out`/`tokens_in_free`/`tokens_out_free`/`calls_made`/`tokens_cached` (process-wide atomics folded from each response's `usage` block) and `TokUsage` + `tokensSnapshot()` (thread-local totals read as a delta = exactly one turn's usage)
- Per-role cost attribution — `RoleCost`, `RoleMax`, `roleCosts()`, `callLog()`, `callLogDropped()`, `resetAttribution()`: one bucket per (role label, model) so a trio-routed turn's tokens land on the model that actually served each role; drained by metrics.zig
- `Caps` + `capsSnapshot()` + `probeCapabilities(...)` — the startup backend probe (native tool support, thinking, context length); `recordLargeToolWall(...)`
- `isLocal(base_url)` — local endpoint detection; `fenceWrites(base_url, model)` — whether file-sized tool calls from this backend/model cannot be trusted and writes must be fenced
- `jstr(gpa, list, s)` — JSON string escaper that sanitizes invalid UTF-8 (borrowed by commons.zig and others)
- `initQuirkStore(io, dir)` — points the learned provider-quirk table at its durable `{dir}/provider_quirks.jsonl` and loads every prior lesson; called at boot by main.zig (server/CLI) and run.zig (each swarm worker) against the same data dir
- `isKeyCfgName(name)` + `KEY_CFG_STALE_S` — which file names are the curl key configs older builds wrote (either transport, per call or per tag) and how old one must be before nothing can still need it; `Supervisor.sweepKeyScratch` reads both
- `isCallBodyName(name)` — which file names are a request body or stream sink that one call wrote under its own name, never a tag's replay copy; `Supervisor.sweepKeyScratch` removes the stranded ones past `KEY_CFG_STALE_S`, and `Supervisor.cleanCastMeta` leaves them alone
- `runCurl(gpa, io, argv, cfg, stdout_limit)` + `KEY_CFG_MAX` — `std.process.run` for a curl whose argv says `-K -`: spawn it with a stdin pipe, write `cfg` into the pipe and close it (`keyToCurl`), then collect stdout and stderr until it exits. The caller keeps `cfg` within `KEY_CFG_MAX` (4096 bytes, what the pipe holds with no reader), because `keyToCurl` asserts it. `postUrl` runs here, and so does every Cloudflare call (`cf_oauth.curl`). `strayCfgByte(value)`, `cfgHeader(gpa, cfg, name, value)` and `cfgEscape(gpa, cfg, value)` sit beside it as the one place a curl config value is checked and escaped: `chatCfg` builds this file's two configs with them, and `cf_oauth` builds the Cloudflare ones

## Dependencies

- `worker/httpc` — the in-process raw-socket HTTP client for loopback backends
- `worker/rate` — rate limiting
- `worker/browser/util.zig` — `sleepMs` for the stream tail loop's 20 ms poll and `retryWait`'s quarter-second slices. Not `io.sleep`: on Windows that parks a plain thread (the chat turn's) on the Io runtime's per-thread alert, and a stray alert there is undefined behaviour in the ReleaseFast build. The poll keeps its pace (~31 ms a lap at the default timer tick, either sleep).
- `curl` (child process) — hosted TLS transport only (and every streamed call); key via `-K -`, a config written into its stdin

## Usage Context

Called from every model-facing path in the worker: `run.zig` mind moments, the chat engine's turn loop, and helper passes in `tools.zig`. `commons.zig` imports it just for `jstr`. `metrics.zig` drains the per-role buckets at the turn's usage choke-point. `config/cf_oauth.zig` imports it just for `runCurl` and `KEY_CFG_MAX`.

## Notable Implementation Details

- Probe-first: a probed capability always wins over the port/model-name heuristics; unprobed backends fall back to heuristics (tested). Per-model quirks self-heal — e.g. a temperature-constraint error rewrites the body and retries — and the lessons are durable: each learn writes through to `provider_quirks.jsonl` in the data dir, so neither a server restart nor a fresh swarm worker re-pays a failed round-trip a previous process already paid (never-lose merge: file fields only fill gaps, RAM lessons stay authoritative).
- **Thinking models get a max_tokens floor** because hidden reasoning eats the budget before the answer; a plain relay model keeps the caller's value verbatim, so it never stalls generating filler. A probed-local thinking model takes `LOCAL_MIN_TOKENS = 2048` up front. A **hosted** reasoning model is caught by a third transport-level heal beside `healParamError` and `healEchoError`, on a signature no vendor owns: the call succeeded, there were no tool calls, reasoning is present, content is empty after trim, and `finish_reason == "length"`. That is a model whose reasoning does not fit in what the caller asked for, and no retry at the same size will change it — so `learnReasoningBudget` records the model, the budget is raised to `@max(budget * 8, REASONING_MIN_TOKENS = 8192)`, and the call retries ONCE with healing off — but only when `healFits` finds the raised call room to finish inside its own deadline. The deadline stops following the budget at `TIMEOUT_CEIL_S` (an 8192-token call already gets the whole 240 s), so an 8x raise of a slow starved call bought tokens with no time to emit them: measured, a reply that starved 8192 tokens in 162 s was raised to 65536 and that retry ran ~236 s for nothing. The pace is the call's own (`call_ms / budget`; prefill, queue and pacing ride inside it, so it errs slow), and the room asked for is `HEAL_ROOM_X = 2` times the starve, not the whole raise: the raised call only has to finish what the starved one began. Asking room for all of `raised` (the first cut) asked an 8x-raised call to fit in 8x the starved call's time, which on a 48-70 tok/s reasoner refused every starve over about 1.5-2K tokens (the engine's 3072-token compaction and handoff never healed) and put the 768-token distillation 22.5 s from refusal, inside its measured 24-62 s first-byte stalls. Now a starved call may take up to half the raised call's deadline; the rescue above (1.48x) stays refused, and the lesson is recorded either way. The stand-in test pins its paces through `test_heal_call_ms` rather than holding the reply. Every later call gets the floor from `effTokens` up front, so the round-trip is paid once, and the lesson persists in `provider_quirks.jsonl` as a `reasoning_budget` flag on the Quirk records (unknown fields are ignored on parse, so no migration).
  This is learned rather than named because the name test was already there and already wrong — `isThinking` answered false for a model that was visibly streaming `reasoning_content`. The engine asked for 768 tokens to distil a turn's continuation state, the answer never fit behind the reasoning, and an empty result is indistinguishable from "the model had nothing to say", so the engine banked a bare compaction note with no state and the next turn began from nothing. Ten turns out of eleven on a live run.
- The per-call wall-clock cap is DERIVED from the output-token budget instead of one flat constant — a flat 90s cap structurally killed exactly the largest, most valuable generations (documented in-file from a real run).
- **The key never touches disk.** `postUrl` and `streamAttempt` spawn curl with `-K -` and a stdin pipe, and `keyToCurl` writes the config (`header = "Authorization: Bearer <key>"` and the content type) into the pipe and closes it. curl reads the config to EOF before it dials, so the close is what starts the transfer, and its own `--retry` resends what it read. All three were checked against curl 8.5, 8.17 and 8.21: the key and the body (`--data-binary @file`) reach the wire, a 503→200 retry resends both, and no request goes out until the close. `postUrl` needs its own `runCurl` because `std.process.run` gives the child no stdin to write. The write never waits on curl: Zig 0.16 gives the Windows pipe a 4096-byte buffer (a Linux pipe holds 64 KB), and a config that long went into a suspended child in 0 ms, where 4097 bytes waited for a reader. So `KEY_CFG_MAX` is 4096, and a key whose config would pass it fails the call before anything is written (`KEY_CFG_TOO_LONG`; the stream falls back to `complete()`, which names it). **A key the config cannot carry fails the same way** (`KEY_STRAY_BYTE`): `chatCfg` builds the bearer line through `cfgHeader`, which refuses a value holding a byte below 0x20 or DEL and escapes the rest. curl reads its config line by line and puts a header value on the wire as it read it, so an unescaped `"` in a key would end the value and a line feed would end the line, and curl would take the rest of the key as options of its own -- a second `url`, which it dials carrying that same bearer, or a `data-binary = "@<path>"`, which uploads that file. Keys come from the user and are not one charset (`sk-...`, `hf_...`, a custom URL's own), so the guard refuses bytes rather than allowing a shape. The test aims an injected `url` at the same stand-in and pins that nothing dials at all, beside a key of punctuation (`"` and `\` included) that still reaches the wire byte for byte; with the guard removed the stand-in receives `POST /injected` carrying the bearer. A curl that dies before it reads fails the write instead of blocking (PIPE_CLOSING on Windows; EPIPE on POSIX, where `Io.Threaded`'s SIGPIPE handler turns the signal into an error). The config used to be a file beside the body: first one per tag that was never deleted (the chat engine's scratch dir is the conversation dir, so a key stayed there for the conversation's life), then one per call, deleted when curl exited. Even that one sat on disk for the whole call, inside a data dir that is often a synced folder, and deleting a synced file only sends the cloud copy to the recycle bin. The request bodies' replay copies (`.llmreq-{tag}.json`, `.streamreq-{tag}.json`) hold no key, so replaying one needs the key from somewhere other than the dir. A server start still removes the configs older builds left (`Supervisor.sweepKeyScratch`). The tests drive the real curl child against a 127.0.0.1 stand-in and look through the call's dir while it is in flight (`MidCall`: at `test_before_curl`, and from the stand-in through `fakehttp.Server.startWatched` while curl waits on the reply) and again after it returns. A config file written for the call's life, before or after the spawn, turns them red. A config of `KEY_CFG_MAX` bytes is handed to a child that never reads (curl created suspended on Windows, `sleep` elsewhere) under a watchdog.
- **The request body is the call's own.** curl reads `--data-binary @file` only when it starts. Calls sharing a dir and a tag run at once, so a single `.llmreq-{tag}.json` let a sibling's write land between a call's write and its curl's read, and that call sent the sibling's prompt with nothing failing. `callPath` names every file a curl call hands curl: `.llmreq-{tag}-{16 hex}.json` for `postUrl`, and for `streamAttempt` `.streamreq-{tag}-{16 hex}.json` plus the sink its reply streams into, `.stream-{tag}-{16 hex}.sse`. A shared sink would have fed a call's tail loop a sibling's reply. When the call returns, after curl has exited, `keepLast` renames each file onto the tag's name (`.llmreq-{tag}.json`, `.streamreq-{tag}.json`, `.stream-{tag}.sse`). The rename replaces the old copy in one step, so a replay never opens a half-written body, and the copy holds whichever call under the tag finished last. If the rename fails, the call's file is deleted. No curl ever reads a tag's copy, so the deleters that name per-tag files (the worker's clean-exit sweep of `.llmreq-{mind}.json`, `cleanCastMeta`) cannot take a body a running call still needs. `cleanCastMeta` also skips every name `isCallBodyName` matches, and `Supervisor.sweepKeyScratch` removes the ones a killed process left once they are older than `KEY_CFG_STALE_S`. Tested with a stand-in per call on 127.0.0.1, calls held by a test seam (`test_before_curl`) until every one had written its scratch.
- Ollama-native handling: `num_ctx` is pinned in options, argument objects are re-serialized into JSON-string tool calls, and the probed model context bounds the engine budget.
- `fenceWrites` fences a hosted backend only on measured text-emission evidence; a probed local backend that cannot parse file-sized tool calls is fenced from round 1.
- Thread-local turn accounting exists because each chat turn runs on its own thread — process-global atomics would cross-count concurrent turns.
- **A chat turn's retry budget** (`RETRY_MAX = 10`, `armRetries`/`disarmRetries`, armed by the engine per turn): on a budgeted thread a hosted call that fails with ANY error — a 429, a 5xx, a transport drop, and just as much an HTTP 401 `Authentication error` or a rejected request — is retried after a climbing wait (`RETRY_WAITS_S`: 5, 10, 15, 20, 30, 30, 45, 45, 60, 60 s — 320 s in all), each wait announced through `retry_notify` as a `provider failed (…): retrying in Ns (i/10)` status frame, where `(…)` is `errHead`: the HTTP status plus the provider envelope's own `message` (`HTTP 401: Authentication error`), else the error's first line clipped to 72 bytes. The count is per provider (base_url + model) and of failures IN A ROW: a reply restores it, so a hiccup costs one wait, a provider that is down for good costs one ladder before every later call to it fails at once, and a misconfigured auxiliary model cannot spend the coding model's retries. Before each retry `retry_rekey` lets the engine hand over a re-resolved credential (the Cloudflare login's refreshed access token — the 401 that used to end long turns), which then serves the rest of the turn (below), and `retryWait` polls `retry_abort` between quarter-second slices of every wait so a chat Stop ends the ladder at once. When the budget is spent (`retryExhausted`) the failure surfaces: the chat call's failure ends the turn with a `gave up after 10 retries` error frame. An unarmed thread (the swarm's workers) and a LOCAL endpoint on any thread keep the older ladder — three retries per call after 10, 20 and 30 s (`RETRY_WAITS_TRANSIENT_S`), transient errors only (`isTransientLlmError`). Both ladders live in `complete()`, which a failed stream reaches through `completeStream`'s fallback; `chat()`/`chatTemp()`/`visionExtract()` and the Ollama-native path never enter either.
- **A re-resolved credential serves the rest of the turn** (`KeySwap`). The engine resolves a turn's keys once, at submission, and passes that copy to every call; the key `retry_rekey` hands a retry used to die with the one `complete()` call that fetched it. Measured on a 20-minute turn whose Cloudflare token expired: each of the ten calls after that paid a silent streamed 401, an announced one, a 5 s wait and a vault read (about 6 s a call) and lost streaming for a blocking fallback. Now `rememberKey` keeps the fresh key per thread while the retry budget is armed, matched on (base_url, the key the caller holds) — another role's key or another endpoint is never swapped, and roles holding the same token share the entry — and `complete()` and `completeStream()` (`swappedKey`) send it in place of the caller's key, so later calls neither pay the 401 nor leave the stream. `armRetries`/`disarmRetries` forget the entries (at most `KEY_SWAPS = 4`, oldest evicted), zeroing each key before its memory goes back (these copies only: each request's curl config and the engine's own copies of the key are freed unzeroed); an unarmed thread keeps none, so a turn nested on its parent's thread (spawnTurn's inline fallback) leaves the parent with no swap, no budget and no re-resolve for the rest of its turn. Tested against a stand-in that tells the keys apart by the bearer curl sent (`fakehttp.Route.has`): after one rotation the next blocking call and the next streamed call make no request with the old key and no re-resolve, and a new turn (arm) pays exactly one 401 and one re-resolve again. Not covered: a 401 on the streamed attempt itself still falls back to `complete()` once per rotation (the stream does not rekey), and the key a turn hands a cast, a scheduled task or a sub-chat is the engine's copy.
- **A stopped turn starts no request** (`stopRequested`, which asks `retry_abort`: the engine's control.jsonl Stop for the turn on this thread, false on any other). It used to be asked only between the slices of a retry wait, so the knob-free re-send, the heals, the stream's fallback and the ladder's own retries all went out after a Stop — measured, a rescue call put a fresh request on the wire 133.8 s after the user pressed Stop. `post()` refuses with `STOPPED` before it dials and again after `rate.acquire` (a 429 cooldown can hold a call for seconds); `streamAttempt` does the same and answers with the shape a Stop mid-stream returns (`stoppedStream`: ok, nothing streamed, so no blocking fallback runs), and `completeOllamaNative` asks for itself, again before an engine-rendered request that came back unusable falls through to `/api/chat`. `complete()` and `chatTemp()` take a failure that a Stop came with as it is — no knob verdict, no knob-free re-send — the ladder checks before it plans (no retry spent, no "retrying" frame), and the starved-reasoning heal keeps the reply the provider did send instead of a refused raised call. A `STOPPED` refusal counts as a Stop without asking again: the engine's predicate answers "no Stop" on any control.jsonl read failure, and a second read that disagreed would have sent the very re-sends the refusal was for. A blocking request already in flight still runs to its own end. `completeStream` no longer counts a stream that brought nothing as the provider answering (`noteProviderOk`). Tested by counting connections at stand-ins: 0 for `complete()`, `chat()`, a stream and the native path with the Stop in, 1 each without; a Stop raised while a hosted call's offline probe runs (after the entry check, before `rate.acquire`) sends nothing from `post()` or `streamAttempt`, so each post-pacing check is proven on its own; a predicate that answers true once leaves a refused call refused (no request, no retry, no knob move); with the Stop landing while a request is out, one request and the knob's trial unmoved, the starved reply kept, one retry spent where two were, and no `/api/chat` behind a raw request.
- **Only a reply can teach the reasoning-off knob.** Auxiliary calls to a model seen reasoning carry a learned knob or the next candidate on trial (`reasonOffFor`), and the reply confirms or retires it (`observeReasonOff`); a call the provider rejected is sent once more without the knob, so a trial never costs the answer. `knobBlindFailure` names the failures that never reached the point where a provider weighs a parameter — HTTP 401/403 (the credential), 408/429/5xx (the provider's clock or capacity), every curl failure and a local timeout, drop or refused connect (the transport), `net.MSG` (no uplink), and a request that never left the process (`KEY_STRAY_BYTE`, `KEY_CFG_TOO_LONG`, an unwritable body, no memory, `STOPPED`) — matched by the module's own constants for them (`ERR_*` in postUrl), never copies. In `complete()` and `chatTemp()` those neither move the trial nor buy the knob-free re-send. `complete()`'s retry ladder resends the same body as for any failure; `chat()`/`chatTemp()` have no ladder, so a knob-carrying aux call that fails blind now ends on its one request (plus curl's own `--retry` of a hosted 408/429/5xx), where the knob-free re-send used to give it a second for the wrong reason. Measured before this: a raised call that ran ~236 s into the provider's own timeout moved a model from `template` to `effort` on no evidence about either, and bought a knob-free re-send that started after the turn had been stopped. A rejection in the body (an HTTP 400 naming the parameter, an HTTP 200 error envelope) still advances and re-sends. Tested by counting requests at a hosted stand-in (probe redirected) for both entry points: a 401 costs one request and leaves the trial alone, a key curl cannot carry costs none and leaves it alone, a 400 costs two and advances it.
- **A streamed call ends when its curl does.** `streamAttempt` tails curl's sink for the `-w` end marker (`\n__VEILSTAT__<code>`), which every transfer curl runs leaves, a failed one included (a refused or timed-out connect leaves code `000`). A curl that fails before its transfer writes nothing: a request body or `-K` config it cannot open exits 26 with an empty stdout (curl 8.5, 8.17 and 8.21). The loop used to leave only on that marker, a finished stream, a Stop, a reasoning runaway or its wall, so such a call sat silent for `--max-time` plus `STREAM_WALL_SLACK_S` (270 s on a local base) before `complete()` ran. Each lap now asks `curlExited` before it reads the sink. It never blocks: Windows reads the exit code off the process handle, and POSIX reaps with `waitpid(WNOHANG)` and clears the `Child`, so its deferred `kill` returns at once instead of signalling a reaped pid (ESRCH, a Debug panic in std). A lap that drains the sink after curl has gone, with no marker in it, ends the loop and logs `stream: curl exited without its end marker`. Tested by deleting the call's own body at `test_before_curl`: the stand-in sees exactly one request, the plain fallback's.
- **A stream has to say it ended.** curl writes its end marker after a `--max-time` cut or a dropped transfer as well as after a finished one, so the marker proves only that curl stopped. `StreamState` records `finish_seen` (any finish_reason) beside `done` (`[DONE]`, or native `done:true`), and a stream with neither that was not stopped on our side (a Stop, the runaway breaker) comes back with `Step.incomplete`: still ok, with whatever content, reasoning and calls arrived, and `truncated` left false because the provider never said "length". Measured before this: a reasoning-only reply cut at the 240 s deadline came back ok and untruncated. The flag keeps such a reply out of the training set's `stop` label (it is recorded as `incomplete`) and out of `noteProviderOk` in `completeStream` (a cut transfer is not the provider answering); what an unfinished reply is worth is the caller's call. A reply returned incomplete logs `stream: ended without a finish_reason or [DONE]`; a stream that falls back to `complete()` instead (nothing streamed, unrebuildable tool calls) logs nothing of the kind, since no reply of its own comes back. The provider gate is tested on a hosted, armed provider with one failure already counted (a full budget cannot show a restore): a cut stream and a stream stopped before it started leave the count as it was, a finished one clears it.
- **Streamed usage is folded across chunks, never taken from the last one.** OpenAI-style providers send one usage block at the end. Workers AI sends usage on every chunk: the first carries the prompt with completion 0, each later one prompt 0 and its own completion delta, and a finished stream restates the totals in its finish chunk before `[DONE]`. A cut stream has no terminal chunk, so overwriting per chunk metered it as its last delta (`in=0 out=2` for a call that read 25220 tokens and wrote 11394), and those zeros reached the turn's spend ceiling and the per-role cost rows. `handleSseStreamLine` keeps the largest prompt count seen and takes the completion as the larger of the summed deltas (chunks with no prompt count) and the last running total (chunks with one), so a finished Workers AI stream counts its total once and a provider that restates a growing total keeps its latest. Tested on the three shapes through `feedStream`, and through the real curl child against a stand-in serving a cut and a finished stream.
