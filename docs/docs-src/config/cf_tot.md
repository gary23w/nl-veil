# cf_tot

**File:** `src/config/cf_tot.zig`  
**Module:** `config`  
**Description:** Tater-tots — autonomous technicians that run the veil's goal loop in the user's own Cloudflare account. This module uploads their runtime (`cloud/tot.js`) through the Cloudflare login, relays the desk's and the CLI's requests to it, runs the jobs a tater-tot is allowed to send to the owner's machine, and launches Agent Garrett beside them when a tater-tot or the owner asks.

---

## Purpose Summary

A tater-tot (a *tot*, short for Tiny Overview Technician) is the goal loop of `worker/chat/goal.zig` with no human in it and no machine of the user's under it. Each tater-tot is a Durable Object in one Worker script, `veil-tots`, that this module uploads into the account behind "Log in with Cloudflare". An alarm is the tater-tot's heartbeat: every alarm runs one iteration (pick, do, measure, record, learn), and its model calls go through the account's own AI binding. An account runs 24 tater-tots (`DEFAULT_MAX_TOTS`) unless its owner sets another limit, up to `MAX_TOTS_CEIL` (1000); the server keeps the limit and sends it with every deployment, and the runtime refuses the one past it. The first is always named Gary. A test here holds the two files to the same numbers.

After the upload this module is a relay. The desk's Tater-tots tab and `veil --tater` ask this server; this server asks the runtime with a bearer token only the two of them know. The token is derived, never stored: HMAC-SHA256 under the server key of the user, the account and a generation counter. The state file (`{data}/u{uid}/cf_tots.json`) holds the runtime's address, script hash, local grants, and the source and revision managed through RSI. Deployment credentials are not stored in it.

The runtime plans each step around an observable result and a verification method. Its judge must cite a numbered tool result and an exact quote before an improvement earns credit; file writes and the agent's own summaries do not prove factual claims. An artifact requested by the human can be verified by reading its content back. Repeated observations earn no further improvement, and `DONE` starts a tool verification step rather than immediately completing the goal. The last measured work and its failures remain in working memory across goal changes. Roaming considers the newest 64 ended goals and rejects near-identical proposals, while a goal explicitly queued by the human can still revisit earlier work.

A tater-tot deployed with `local` may queue jobs for the veil on the owner's machine. Nothing listens at home for them: a background thread polls each approved tater-tot's queue every 20 s, runs a job as an unattended chat turn through the same entry points a scheduled task uses, and posts the turn's final answer back. The approval is a checkbox at deployment and is recorded in this server's state file, so a runtime that claimed the grant for itself would find no bridge.

## Key Exports

- `SCRIPT`, `MAX_TOTS`, `PRIMARY` — `"veil-tots"`, `3`, `"Gary"`
- `validName` — a tater-tot's name: 1-24 of letters, digits, `-`, `_`, starting with a letter (it becomes a URL segment and part of a conversation id)
- `listTots` — `GET /api/v1/tots`: the roster as the runtime reports it, plus connected / deployed / reachable / current, the address, the local grants and the last deployment error
- `createTot` — `POST /api/v1/tots`: uploads the runtime when the account lacks it or runs another build's, then creates the tater-tot; a `local: true` body records the grant
- `deleteTot` / `teardown` — `DELETE /api/v1/tots/:name` removes one tater-tot, and when it was the last one the Worker script too (the answer says `worker_removed`); `DELETE /api/v1/tots` removes the script and everything every tater-tot stored. Both forget the deployment, every grant to this machine and the token generation the script held
- `totEvents` / `totCommand` / `totConfig` — the event tail, a command or message, and the settings (`model`, `pace_s`, `size`, `daily_calls`, `charter`, `paused`; never `local`)
- `setLimit` — `POST /api/v1/tots/limit {max}`: how many tater-tots this account may run, 1 to `MAX_TOTS_CEIL`, kept in the state file (`max_tots`, 0 = the default) and sent with every deployment; lowering it under the count stops new deployments and deletes nothing. How many an account really carries is its Cloudflare plan's to say
- `listRuns` / `runEvents` — `GET /api/v1/tots/runs` and `GET /api/v1/tots/runs/:run/events`: every deployment kept under `_tots/` (live, ended, failed), newest first, and one run's events read from its `events.jsonl` with the runtime's own `after`/`limit` semantics; `forward=1` reads the first `limit` past `after` instead, from the run's first event on, which is what `veil --tater verify` walks to recompute the evidence chain. `runLeafOk` is the folder-name rule (`<name>-<YYYYMMDD-HHMMSS>`)
- `setKey` — `POST /api/v1/tots/keys`: a key becomes a secret binding of the Worker (it rides curl's stdin, never a file here); an empty value removes it. The names: `brave`, `google`, `google_cx` (search); `alert` (the guard's webhook, an https URL: a tripwire, a recovery, a leash land there as one JSON POST a Discord or Slack webhook renders as it is); `garrett_url` + `garrett_token` (an Agent Garrett the owner deployed by hand). The runtime's own token is not a name it accepts, and an address key must be https
- `garrettStatus` / `garrettLaunch` / `garrettRemove` — `GET`, `POST`, `DELETE /api/v1/tots/garrett`: Agent Garrett (github.com/gary23w/garrettstimpson.ca/agent) as this server and the runtime know it, launched now, or removed. `launchGarrett` reads the agent's five modules from the repo (`GARRETT_SRC`; the stand-in serves them under `/garrett/src/` while the API is a loopback), uploads them as one Worker, `veil-garrett`, with its AI binding, its three Durable Object classes and the policy its own `wrangler.toml` ships (safe mode, confirmation required, no active and no dark-web tools over MCP), sets three derived secrets on it (its MCP bearer; a password locking the chat UI, which is open to anyone with the address otherwise; a session secret), enables its workers.dev address, and points the tots at it with two secrets on their own Worker, `GARRETT_MCP_URL` and `GARRETT_MCP_TOKEN`. `?reveal=1` on the status adds the chat UI's password (derived, so it can always be shown again). A tot asks through its `garrett_launch` tool: the runtime's pad records `pending`, and `syncGarrett` launches on the next mirror pass and posts the result to `/v1/garrett/result`; a refused launch waits a quarter of an hour. Removing the last tater-tot, or the runtime, removes Agent Garrett with them
- `totConfig` and `createTot` take two more settings the runtime keeps: `posture` (`normal` | `defend`) and `leash_s` (0, or 60 to 604800 seconds); see the runtime's day-after kit below
- `padRead` / `padWrite` / `padClear` — the scratchpad the account's tater-tots share; clearing it first keeps the local copy as `_tots/scratchpad-<when>.md`
- `totFolder` — a deployment's local folder, `u<uid>/_tots/<name>-<YYYYMMDD-HHMMSS>` (UTC): one per run, so a tater-tot deployed again under the same name never writes into the old one's
- `bgLoop` — the tater-tots thread: every 20 s the owner's-machine bridge, every third pass the local folder mirror (and the replacement of a runtime an older veil uploaded)

## Usage Context

`main.zig` registers the nine routes, lists this file in its route-gate audit (`ROUTE_MODS`) and starts `bgLoop` beside the scheduler thread. The desk reaches the routes through `netcli.tots*` (poller.zig, only while the Tater-tots tab is on screen); the CLI through `cli/tot.zig`. Every route is admin-gated like the scheduled tasks: a tater-tot spends the account's Workers AI, and one with the owner's machine starts full-tool turns there.

## The day-after kit (runtime VERSION 8)

What a tater-tot does when the model is gone, the lab is quiet and attribution is the fight. The guide page `guide/day-after` maps it to the scenarios; this is what the runtime and this module actually do, all of it covered by `cloud/tot.test.mjs` and the tests here.

- **The guard** (`/guard add|rm|clear`, `veil --tater guard`): targets the owner names - a page, with words it must show (`--text`), a status it must answer (`--status`), or its content pinned (`--pin`); a DNS name's answers by record type (`dns:<host> --type A|AAAA|NS|MX|TXT|CNAME|CAA|SOA`, over DNS-over-HTTPS) - looked at every heartbeat before the model is asked and without one, at most 16 per tot, at their own cadence (`--every`, 30 s and up). The alarm fires at the guard's cadence; the goal loop keeps its own next time (`loop_due`), so a dead, rate-limited or withdrawn model and a spent daily budget never stop the watch. A change of state is a **tripwire**: a chained `tripwire` event, a scratchpad entry every tot of the account reads, a directive in the tot's inbox (its next iteration is brought forward, and reads the tripwire as outranking its plan), and - with the `alert` key - one JSON POST to the owner's webhook. A pinned page's content changing, or a DNS answer changing, is noted once (`CHANGED`) and becomes the new baseline. The guard's checks always name the tot (`User-Agent: veil-tot/8 (<name>; +https://github.com/gary23w/nl-veil)`).
- **The evidence chain**: every event carries `prev` and `hash`, SHA-256 over the previous hash, the seq, the time, the kind and the text, so the `events.jsonl` the mirror writes is tamper-evident on its own. `veil --tater verify <run>` walks a run from its first event and recomputes the chain on this machine (`cli/tot.zig` `chainHash` / `Chain`, held to the same vectors as the runtime's test); an altered row, a dropped row and a row from another run are named. Events from before VERSION 8 are counted as unsigned, not judged.
- **Posture DEFEND** (`/posture defend`, `--posture`): the runtime is frozen (`runtime_edit` and `runtime_deploy` are refused; `runtime_read` stays), a CAPTCHA or bot check is reported and not worked through, every request the tot makes names it whatever the model asked for, and the prompt holds it to read-only verification and reporting with evidence unless the human asks for more. `/posture normal` restores the ordinary prompt.
- **The leash** (`/leash <seconds>|off`, `--leash`): every call from the owner's veil (the mirror's roster poll once a minute, the desk, the CLI) is contact; with a leash set, no contact for that long holds the goal loop - said once, and the webhook hears it - while the guard goes on, and any call releases it. A tot never runs on with nobody's veil alive anywhere. Opt-in: 0 by default.
- **Agent Garrett**: see `garrettLaunch` above. In the runtime, `garrett_tools` lists the agent's tools over MCP (`tools/list`, with the argument names they take) and `garrett` calls one (`tools/call`, the stateless legacy form: no protocol header); the text comes back with its evidence metadata, and a tool the agent's operator did not allow comes back as `FAILED`. Both exist only while both secrets are set; `garrett_launch` exists until then and asks the pad.
- Proven: every piece above against the stand-ins (the node suite, the Zig suite). Not yet proven live: a tripwire on a real account's Worker, a real Discord or Slack webhook rendering the POST, and the Agent Garrett launch against the real Cloudflare API (the upload mirrors the agent's own `wrangler.toml`; the modules are fetched from `main`, so the agent's own changes land at the next launch).

## Notable Implementation Details

- Deployment checks the runtime with a read-only roster request before sending the create request once. An unreachable cached runtime is uploaded and reconnected once, preserving saved source and Durable Object storage. Enabling the workers.dev route must succeed; provider failures are reported instead of silently becoming a generic startup delay.
- `deleteRun` (`DELETE /api/v1/tots/runs/:run`) removes a saved run from history by writing `.hidden` in its existing folder. It validates the run name, scopes the path to the authenticated user, and preserves all status, event and note files. Removing the marker restores the entry.

- Runs: every deployment is a run with its own folder (`totFolder`: name + start time), so a name deployed again is a new run. A deployment that fails is kept as a run too (`recordFailed`: `status.json` with `state: failed` and the error, two events), and `createTot` answers `{ok:false, err, run}` so the desk can open it. `deleteTot` mirrors the tot one last time before the runtime forgets it, then marks the run `deleted` (`markEnded`); the desk reads an ended run's console from its folder.

- CAPTCHA and bot-check pages remain actionable: `pageText` returns their text and numbered controls, and `web_search` keeps a browser challenge open for the tot to complete. The prompt directs the tot to solve the challenge, verify access and continue; detecting one does not mark the tool action as failed.

- Runtime RSI: `runtime_read`, `runtime_edit` and `runtime_deploy` expose the actual shared `tot.js`, including prompts, tools and stop rules. The pad stores source in chunks and applies revision-checked edits transactionally. `syncRuntime` seeds the source, uploads pending revisions through the owner's Cloudflare login, and reports the result to `/v1/runtime/result`. No proposal, privileged-code approval or local execution grant is required. Uploads preserve the existing bindings and secrets; compiler failures leave the deployed source intact. `State.runtime_source` and `runtime_revision` keep successful self-edits across restarts and normal deployments. The owner's veil must be running and connected for uploads; cloud work continues on the last deployed revision while it is offline.

- Seen working on a real account (the folders `mirrorTot` writes): three runs of a tater-tot named Gary on the one-word goal `test` at a 5-second pace improved 1 of 18, 21 of 49 (24 files of reports, 12 lessons) and, on the runtime that writes a checklist for a vague goal first, reached 6/6 of that checklist by iteration 11 with a `test_runner.py` it wrote and ran (3 of 3 passing). That run also showed a model answering in its native tool-call markup (`nativeCalls` / `pickText` in tot.js now read it) and a script missing the files it did not name (a script that names none now gets the workspace, newest first, up to `PY_FILES_BYTES`). The README's "Seen working" has the excerpt; the trailer is `docs/video/tots-release.mp4`, drawn by `docs/video/render`.

- The move from hots: until 1.1.8 a tater-tot was called a hot, with the Worker `veil-hots` (and `veil-hots-py`), the state file `cf_hots.json` and the folder `_hots`. `moveFromHots` finds that state and, when the login is the same Cloudflare account, reads the old runtime with the token it was given (`tokenWith` under the old label), creates each hot again as a tater-tot through `deploy` (its name, its goal while that was active, its settings and its owner's-machine grant; `movedReq`), sends its files and its pause through `POST /v1/tots/:name/import` in batches under `IMPORT_BATCH`, carries the scratchpad through `POST /v1/pad/import`, and marks the old state `moved`. Only then does it delete the old Workers, rename `_hots` to `_tots` and drop the old state file. No answer from the old runtime moves nothing and removes nothing; a tater-tot that already exists from an earlier attempt is carried on with, not created twice. It runs from the background pass (`moveIfDue`, a quarter of an hour after a failure) and before a deployment (`createTot`), so a new tater-tot never lands beside a Worker still running under the old name; `listTots` says a move is pending, and `teardown` removes an old deployment that was never moved.

- Native Python packages: a running script cannot fetch code that is not pure Python, so `pyUploadBody` names a set of packages as empty modules of type `text/x-python-requirement` and Cloudflare supplies its own builds. `PY_NATIVE` lists the sets, most first, ending with none; `uploadPython` takes the first set the API accepts. An accepted upload can still be a Python that does not start, so the state carries `py_check`: on each mirror pass `checkPython` asks the runtime `GET /v1/python` (does the Python Worker answer, and with which native packages). Yes settles it and records `py_native`; no, twice in a row, uploads the next smaller set; an answer that is not the runtime's (a deployment still coming up) is asked again, `PY_CHECKS` times at most.

- The runtime's upload carries four modules when the account takes them all: `tot.js`, and - the tater-tot's mind - `neuron-db.mjs` with `neuron_core.wasm` (the veil's memory engine compiled to WebAssembly, `application/wasm`). tot.js imports the two by name only when it first needs them, so an upload without them is still a working runtime that recalls by keyword. The ladder is: everything; without the browser; without neuron-db; without Python. The state records `python`, `browser` and `neuron`.

- Two scripts go up. `veil-tots-py` (cloud/tot_py.py, the `python_workers` flag, a `text/x-python` module) runs a tater-tot's Python and has no public address; the runtime reaches it through a service binding, `PY`. The runtime's upload also asks for Cloudflare's browser binding, `BROWSER`. Both are optional: the runtime is uploaded asking for everything first, then without the browser, then without Python, and the first upload Cloudflare takes wins. The state records which the tater-tots have (`python`, `browser`) and, for one that is missing, Cloudflare's own refusal (`tools_note`); the roster serves them so the tab and `veil --tater` can say so. Removing the runtime removes the Python Worker after it.

- The local folder: each pass reads the roster, which carries every tater-tot's event seq and notes revision and the scratchpad's seq, and asks for the rest only when one of them moved, so an idle account costs one call a minute. Events are read forward from the folder's own cursor (`.mirror.json`) and appended to `events.jsonl` and to `events.log` as `<UTC time>  r<iteration>  <kind>  <text>`, the text's own line breaks indented under it. Notes changed since the newest stamp held are written to `notes/`, and files of notes the tater-tot deleted are removed; a note name outside the runtime's charset is never written. A deleted tater-tot keeps its folder.
- Text limits: a goal or charter may hold `modelcfg.goalCharLimit(model)` characters, about a tenth of the model's context window (800 to 4000), the same function the desk's form counts against. The server refuses past it and sends the limit to the runtime as `text_max`, which clips a later `/goal` or `/charter` to it; changing a tater-tot's model sends the new model's limit.
- Before RSI is seeded, an older runtime is replaced in place from this build. Once the tots own their source, ordinary upgrades and deployments preserve it, including drafts based on it. Companion-module changes may still trigger an upload with that saved source; Durable Object storage is kept.

- The upload is five calls, in this order: read the account's workers.dev subdomain, ask whether the script exists, `PUT` the script (multipart: metadata + module), `PUT` the `TOT_TOKEN` secret, enable the workers.dev route. The metadata names the `AI` binding and the `Tot` object class and carries `keep_bindings: ["secret_text"]`, so the token is never part of a body that has to ride a file. The class migration (`new_sqlite_classes`) rides a first upload only; because the existence check is only a hint, an upload refused one way is tried the other way once and the first refusal is the one reported.
- A deployment whose saved hash matches the account's chosen source and companion modules costs no Cloudflare upload. A different hash uploads those modules before creating the next tot; tater-tots already running keep their storage.
- The runtime's address must be `https://<name>.workers.dev`. A loopback address is accepted only while the Cloudflare API itself is a loopback stand-in (`NL_CF_API_ROOT`, the tests): there the stand-in plays the account's workers.dev too. A state file edited to name any other host gets no call, so the token cannot be sent elsewhere.
- A workers.dev address enabled a moment ago may answer with Cloudflare's own page for a few seconds. Deployment checks readiness with GET (up to nine attempts, 2.5 s apart) and repairs stale cached setup once. The create POST is sent only after readiness succeeds and is never replayed automatically; a lost reply asks the owner to refresh live tots before trying again.
- A job's conversation is `tot_<name>_<job id>_<queued at>`. The stamp keeps a job from a tater-tot that was deleted and deployed again under the same name out of the old tater-tot's conversation. One job runs at a time per tater-tot; a conversation that already has an answer is posted, not rerun, so a restart mid-job loses nothing; a conversation with messages and no answer is reported as a failed run.
- The bridge walks only admin accounts, as the routes do: a state file is just a file, and it must not start full-tool turns for an account that could not have deployed a tater-tot.
- cloud/tot_py.py gives a script what a Worker's Python lacks: `requests` and `urllib.request.urlopen` on the Worker's fetch (in place where Pyodide's `run_sync` can wait; otherwise the script is stopped at the request and run again with the answer), an installer that unpacks pure-Python wheels from PyPI on a missing import or a `pip install`, and a `subprocess` that answers pip itself and refuses everything else in words. The tater-tot remembers its packages (`py_packages`) and sends them with each script. cloud/tot_py_test.py runs all of it under CPython against a loopback web and PyPI.
- The first Python Worker and the browser binding ran on a live account; the additions above have not yet. The browser's session protocol (`POST /v1/devtools/browser?keep_alive=`, then a WebSocket at `/v1/devtools/browser/<session>` carrying DevTools JSON) was taken from Cloudflare's own client source; the Python Worker follows Cloudflare's documented entry point. Against the stand-in, the Python Worker's code ran under the real interpreter.
- Verified against a stand-in API (`worker/fakehttp.zig`), end to end against a local stand-in that imports the uploaded script and serves it (deploy, the limit, the folder mirror, clearing the pad, deleting one tater-tot and then the last), and by a first deployment on a live account (deploy, iterations, web fetches, notes, lessons, an inner swarm). Replacing an older runtime in place and removing the Worker with the last tater-tot have run against the stand-in only.
