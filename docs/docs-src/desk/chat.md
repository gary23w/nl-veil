# chat

**File:** `desk/src/chat.zig`  
**Module:** `desk`  
**Description:** The veil-desk Chat tab client and renderer — it sends a message to the server-side chat brain, streams the turn's event frames back into the UI, and steers or stops a running turn. The agentic loop itself now lives in the backend (`src/worker/chat/engine.zig`), not here.

---

## Purpose Summary

chat.zig is the desktop's chat worker thread (beside the UI and the poller), owning its own std.Io and communicating with the UI only through a locked Store. It is a **thin client** over the server chat brain: a user message is POSTed to `/api/v1/chat/convs/:id/messages`, the turn's frames are streamed from `/events`, and a line typed while a turn runs — or the Stop button — becomes a `/control` op (`steer` / `stop`) the running server turn folds in. The heavy machinery — the tool-calling loop, casting, the auto-loop drive, the neuron-db learning harness — runs server-side in `worker/chat/engine.zig`; the desk's job is to send, render, and steer.

The desk prefers the backend turn and **falls back to its own local engine** on any failure (a `501` from the kill switch `VEIL_CHAT_BACKEND=0`, a non-2xx, or an unreachable server), so the Chat tab keeps working even when the backend is disabled. It also owns chat-side presentation: conversation selection, streaming/render of the frames, the memory/proposal panes fed by the server, and settings.

## Key Exports

- `Chat` (struct) — the chat client: state fields + methods; instantiated once and `run()` on its own thread
- `Chat.run` — the ~10Hz tick loop: drains UI commands, drives the send/stream/steer flow against the server, publishes render state
- `Chat.cmdSend` — entry for a user message: POSTs it as a turn to the server chat brain, arms the auto-loop tier for the conversation
- `Chat.cmdStopCast` / control helpers — post `{"op":"stop"}` / `{"op":"steer",…}` to the running turn's `/control`
- conversation lifecycle + message-render primitives that mirror the server's `messages.jsonl` / `events.jsonl` shape

## Dependencies

- store.zig (Store — the lock-guarded shared UI/state surface)
- llm.zig (streaming client — used for the LOCAL fallback engine when the backend is unavailable)
- netcli.zig (in-process server calls: POST the message, poll `/events`, POST `/control`)
- scan.zig (filesystem-first cast watching for the swarm board)
- neuron.zig (neuron-db bridge — used by the local fallback; the server owns memory for backend turns)
- httpc.zig (curl-free loopback HTTP), catalog.zig, secrets.zig, log.zig, std.Io, builtin

## Usage Context

Instantiated once and launched on its own thread at app startup. The UI thread never calls its methods directly — it pushes typed commands into a Store queue (send, new/select/rename/delete conv, stop_turn, steer, loop_kick, save_settings/key) which the tick loop consumes. It talks to the running nl-veil server on :8787 for the whole chat flow; when that backend is unreachable or disabled it degrades to the bundled local engine rather than failing.

## Notable Implementation Details

The server owns the turn: one in-flight turn per conversation (the server answers `409` on a racing send), the tool loop, the auto-loop drive tiers (off / on / afk, passed as `loop: 0|1|2` on the message body), and the learning harness all run in `worker/chat/engine.zig`. The desk streams the turn's frames positionally from the `/events` cursor and renders assistant tokens, tool starts, and status lines. Steering is cooperative: a line typed mid-turn is posted as `{"op":"steer","text":…}` and folded in server-side without restarting the turn; Stop posts `{"op":"stop"}`.

The **local fallback engine** is the desk's own earlier chat brain, kept as a resilience path: if the backend turn can't be used it runs the turn locally (its own stream, tool recovery, and neuron-db scopes). This is why the desk still bundles llm.zig and neuron.zig even though the backend normally does the work.

**Selecting a conversation re-mirrors it, unconditionally.** `loadMsgs` used to re-mirror only when the conv id started with `"scheduled_"` — a NAME standing in for a PROPERTY. Any conversation driven through the chat API grows server-side under an ordinary id: a second desk, a remote client, the simulation harness. Selecting one showed a frozen snapshot (typically the prompt with no reply, reading as "the task never executed") that never updated, and because `mirror_live` is only set during a mirror the live event poller never attached either, so nothing arrived after the fact. Observed live: a run mirrored at 924 bytes on its first turn while the server's copy passed 400 KB. Every select now re-mirrors, and the old `remirror` parameter (which forced this for a conversation returning from the background) is gone as subsumed. What makes that safe is a **shrink guard** in `mirrorServerConv`: when the server reports fewer messages than the local mirror holds, the local file is kept and the mirror reports success — turns can legitimately run on the local engine against a reachable server, so the local copy can be a superset, and an unconditional re-mirror without the guard would silently delete those. The count deliberately excludes the `{"title"}` header row (it has no `"r"` field), and the mirror log line now reports message count alongside bytes.

**A cast is watched in the tree the server spawned it in.** `watchCast` has to find a cast's run dir before it can tail its events.jsonl, fill the Activity row and point that row's Stop at the run, both for a cast the desk fired (`fireCast`) and for one the server veil fired, which `startServerCastWatch` only displays. It used to walk `scan.listSwarms` and take the first run dir whose basename was the raw conversation id (or the cast's hex id). The server maps the id first (`worker/chat/paths.zig` `buildRootRel`): a sub-chat (`<primary>__sN`) casts into its primary's `_chat/builds/<primary>`, and a scheduled run (`scheduled_<task>_<stamp>`) into `_sched/<task>/runs/<stamp>`, a tree that walk never entered. So in a sub-chat a desk-fired cast failed at its deadline with "the run directory never appeared", a server cast never showed its run, and the row's Stop reached no run dir; no cast in a scheduled run was ever found. `castRunTail` now maps the conversation the same way (the tree `chatBuildRel` names for that chat on screen, without the account), and `scan.findRun` looks for `u<uid>/<that path>/events.jsonl`, or the default `u<uid>/<hex>` of a cast fired with no conversation, under every account dir, keeping the newest. It is a lookup rather than a filtered walk because the watcher already knows the path: a few stats find it, where the roster walk weighs every run dir on disk and keeps only the newest 64. A test arms both watches (the state `fireCast` leaves, and `startServerCastWatch`) for an ordinary chat, a sub-chat, a scheduled run, a scheduled run's sub-chat and a chat whose cast ran under another account. Each must find the run dir the server spawned; the desk's own watch must also wait until the hive has started, and its row's Stop must land in that dir. A scan.zig test holds `findRun` to account dirs, the newest run and unclipped ids.

**The Memory tab reads the store the server writes, and re-reads it when the server says it changed.** The server keeps one durable store per account, `{data}/u{uid}/.veil-desk/memories.jsonl`, and at startup copies the pre-split global `{data}/.veil-desk/memories.jsonl` into `u1`'s once (`migrateLegacyMemories`, which keeps the original). The desk went on reading the global file, so the tab showed a snapshot frozen at the migration, a fact the veil had just recorded never appeared, and a card deleted in the tab was back in the prompt next turn. `memoriesPath` now returns the per-user file whenever it exists, taking the uid from `uidPrefix` (the bound build dir's leading `u…` segment, else `u1`), and falls back to the global file only until the server has created it. Every desk path to the store goes through it: `refreshMemory` (the tab's rows, which also feed the local engine's YOUR MEMORY block), `storeMemory`, `forgetMemory` (the tab's delete button, sent as the `.forget_mem` command), `ensurePatUsable` (the GitHub PAT lookup that keeps memory and the git tools' token store in sync) and, through `storeMemory` and `forgetMemory`, `processMemory`, the local engine's REMEMBER:/FORGET: parser. The tab also used to load only at startup and after its own edits. `renderScFrame` now re-reads the store on the server's `{"kind":"memory"}` frame, which the engine's `emitMemoryUpdated` sends after each applied batch, and again on `{done}` to catch a frame missed across a reconnect or a cursor skip; `serviceBgFrame` re-reads on the memory frame for a conversation the user switched away from, because the store is global, not the conversation's. Two parsing tolerances mirror the engine. `memLine` (twin of the engine's `durableLine`) strips a UTF-8 byte-order mark, as an editor or PowerShell `Out-File` leaves ahead of the first record; behind it the oldest memory was invisible to the tab, the prompt block and FORGET:, and the forget rewrite carried the mark through. `memoryDirective` (twin of the engine's function of the same name) finds the keyword after a `-` or `*` bullet, a `>` quote, emphasis or a code span (`- REMEMBER: …`, `**FORGET:** …`) and strips that dressing from the body, where the exact-prefix match had left such a line in the shown reply and the store unchanged. Two tests pin both behaviors against a real directory.

**A pushed file lands in the conversation it was pushed for, whichever one is on screen.** The server sends files down as `{"kind":"file_sync","path","content"}` frames, a finished hive's output among them (engine `maybeSyncCastFiles` → `emitRunFiles`). Normally only a desk that does not share the server's data folder receives them, because on a shared disk the sync probe short-circuits the push. `applyFileSync` used to write into `chatBuildRel`, the on-screen conversation's tree, and `serviceBgFrame` skipped the frame, so a hive that finished in a chat the user had switched away from never delivered its files to this machine. Both handlers now pass the frame's own conversation (`sc_conv` in the foreground, the background slot's id otherwise), and `applyFileSync` writes under `delegatedWorkdir(conv)`: the directory that conversation's delegated tools run in and `answerFilePull` reads from when the server pulls a file back. The `safeSyncPath` check still runs first, and a frame with no conversation writes nothing instead of taking `delegatedWorkdir`'s fallback, the data dir itself. The console/git binding (`syncBuildDir`) follows only when the file landed in the on-screen chat's tree; a sub-chat family shares one tree, so a push for the primary still binds a sub-chat on screen.

**One conversation → build-tree mapping, the server's.** `buildRelFor` resolves an explicit conversation the way `worker/chat/paths.zig` `buildRootFromChatBase` does: a sub-chat (`<primary>__sN`) to its primary's tree, a scheduled run (`scheduled_<task>_<stamp>`) to `_sched/<task>/runs/<stamp>`. `chatBuildRel` is `buildRelFor` of the active conversation. The delegated paths (`launchDelegated`, `answerSyncRequest`, `answerFilePull`) used to go through a separate copy that missed both redirects, so a sub-chat's delegated tools ran in `builds/<primary>__sN/work` while the server, the Files tab and the console used the primary's tree, and the same-disk probe missed there. The desk's test build imports the server's `paths.zig` as `chatpaths`, and a test holds the two mappings to the same answers; three more pin the push itself (background, foreground, refused).

**Model-call scratch dirs, and the key sweep.** The local engine's turn stream, the background judge and the act router each make their desk model calls (`llm.start`) in a scratch dir of their own under `{data}/.veil-desk`: the sidecar itself, `judge/` and `router/`. `LlmScratch` names the three and `llmScratchDir` resolves them for every `llm.start` caller. No call writes its API key there now (llm.zig hands curl its config over stdin), but older builds did: builds before 2026-09-17 left a fixed `.chatcurlcfg` in each dir for good, and the builds after them left a call's own config when a desk was killed mid-call. `sweepLlmScratch` removes stale configs (`llm.sweepKeyCfgs`) from the top level of those three dirs and nowhere else. `run()` sweeps before any model call starts, then every ~5 minutes (`tick % 3000`): a config younger than `llm.KEY_CFG_STALE_S` could still belong to a live call of an older desk build on the same data dir, so the first pass keeps it and a later pass takes it once it ages out. Each pass that takes any logs `key scratch: removed N stranded curl config(s)`. A test lays out stale, young and keyless files across the three dirs and `chats/`, and checks every file's fate, the count, and that a second pass takes nothing.

**The git tools' token files, in the same sweep.** `runGitTool` hands `repo_create` and `git_push` the sidecar (`sideDir`), and each call writes its own GitHub token file there, a curl config or a git credentials file, deleted once its child has exited (see the gitvc case file). A desk killed mid-call strands one, and builds before 2026-09-17 did so under the fixed names `.ghcurlcfg` and `.gitcred`. `sweepGitScratch` runs `gitvc.sweepTokenFiles` over the sidecar's top level, with gitvc's own names and floor (`gitvc.TOKEN_FILE_STALE_S`). `sweepKeys` runs both sweeps and returns both counts, so each `sweepKeyScratch` pass (at startup and every ~5 minutes) that takes a token file also logs `key scratch: removed N stranded GitHub token file(s)`. Each sweep keeps to its own module's names because the two floors rest on different bounds: a model call ends within its total timeout, while a push has no timeout and is kept young by a lease instead. A test lays out stranded, live and keyless files across the sidecar, `judge/` and `chats/`, and checks every file's fate, both counts, and that a second pass takes nothing.

**`::pat` refuses a token the git tools would refuse.** `cmdSaveGithubPat` saves the pasted token, trimmed, to the store the git tools read and to a "key" memory. Before 2026-09-17 it saved any bytes. A token with a byte no GitHub token has (`gitvc.strayTokenByte`: anything but ASCII letters, digits and `_`) could write curl options or credentials lines of its own at each `repo_create` and `git_push`, which now refuse it too (see the gitvc case file). Such a paste is now neither saved nor remembered, and a token already stored stays. The `Token NOT saved` notice names the byte and its place, never the token. A test saves a well-formed token pasted with whitespace around it. It then pastes four bad ones: one that writes a curl `url` line, a quoted one, one wrapped across two lines, and another service's key. For each it checks the notice, the stored token and the memory file.

**The console's commands ask nobody for a credential, and the two doors differ over which nobody.** A micro-console command runs as a child of the desk (`consoleStart`), and on Linux and macOS that child inherits the desk's controlling terminal. Anything needing a credential — `git push`, `git clone https://…` — therefore asked on `/dev/tty` and waited: the question appeared in whatever terminal the desk was started from, where nobody is looking, and the command burned its whole deadline (60s on the AI `RUN:` door, 300s on the You tab). Measured 2026-09-17 with git 2.43 in WSL, run the way the console runs it (`sh -c`, under a pty, against a 127.0.0.1 stand-in that answers 401): git printed `Username for 'http://…':` onto the pty and was still sitting there when its bound killed it. `consoleEnviron` now builds the child's environment — the desk's own (`llm.osEnviron`), given the treatment `gitvc.zig`'s `gitEnviron` gives the desk's own git children — with `GIT_TERMINAL_PROMPT=0` on **both** doors, because neither tab can answer a terminal prompt: a command's stdin is the null device and its output is a sink file polled into the scrollback, so there is nothing to see and nowhere to type. git gives up in under a second instead. The **askpass** is where the doors part, because it is a dialog. The AI door empties `GIT_ASKPASS`, which also stops git consulting `core.askPass` and `SSH_ASKPASS`: nobody can answer for the model, whose command would otherwise pop a credential dialog over the user's desktop, unasked, and wait out its turn. The You tab keeps whatever askpass the desk inherited, because a person who configured one and just typed `git push` there is exactly who can answer it — and in the same WSL run that path still worked, answering and reaching the remote in under a second. Keeping it costs one thing: a dialog that waits for its person, which the tab cannot show is waiting, can still eat the 300s deadline. So `consoleCredentialNote` speaks in both cases. git's own `terminal prompts disabled` becomes a line naming what to use instead — the git tools on the AI door, a credential helper or the Veil's `::pat` token on the You tab — and a You command that times out while an askpass is named says the dialog is off-screen rather than leaving a bare timeout. The note rides out with the status note, so the scrollback and the model's fold both carry it. A `test_console_environ` seam decides what the child inherits before `consoleEnviron` has its say, without which the checks pass vacuously: the PowerShell these checks run from already sets both variables. Three tests — one runs a command on each door and reads back the environment it actually got, one holds the note to git's words and to the doors, one forces a You command onto its deadline with and without an askpass named. What this does not cover is a program git starts for a remote or a signature (`ssh`, `gpg`), or any other command that opens `/dev/tty` itself: `std.process.spawn` offers `pgid` but not `setsid`, so the console cannot take that terminal away.
